# 揭棋 AI 实现调研与优化方案

> 本文档梳理当前人机对战 AI 的实现方式、存在的瓶颈，以及后续可落地的优化路线图。
> 调研依据：`src/ai/`、`src/engine/moves.ts`、`src/stores/gameStore.ts` 当前代码。

---

## 一、当前 AI 是怎么实现的

### 1.1 整体架构

```
UI 点击 / 自动触发
   └─> gameStore.requestAIMove()
          └─> 向持久化 Web Worker 发送 { type:'search', state, config:{maxDepth:6, timeLimit:3000} }
                 └─> worker.ts (常驻，复用同一张置换表)
                        └─> search.findBestMove()
                               ├─ 迭代加深 (depth 1 → 6)
                               ├─ PVS 主搜索 + 静态搜索
                               └─ 返回 {from, to}
          └─> executeMove() 落子
```

关键点：
- **Worker 常驻**：`newGame` 时创建一次，`cleanup`/`newGame` 时才销毁，对局内所有回合共用同一个 `TranspositionTable`，跨回合缓存复用。
- **异步不阻塞 UI**：搜索在 Worker 线程跑，主线程只负责通信与落子；带 5s 超时保护，超时回退到随机走子（`fallbackAIMove`）。
- **当前强度配置**：`maxDepth = 6`，`timeLimit = 3000ms`（见 `gameStore.ts:200`）。

### 1.2 搜索算法（`src/ai/search.ts`）

采用的是工程象棋 AI 的标准组合拳，已具备相当完整的搜索框架：

| 技术 | 实现位置 | 说明 |
|------|----------|------|
| Negamax + Alpha-Beta | `search()` | 负极大形式，天然对称 |
| **PVS（主变量搜索）** | `search():271-281` | 第一个着法全窗口，其余零窗口，失效再重搜 |
| **迭代加深** | `findBestMove():371-417` | depth 1→6，逐层利用上一轮结果 |
| **期望窗口（Aspiration Window）** | `findBestMove():376-380` | 用 `bestScore ± 150` 缩小窗口加速 |
| **静态搜索（Quiescence）** | `quiescence():68-133` | 叶节点只续算吃子，消灭"地平线效应" |
| **空着裁剪（Null-Move）** | `search():244-255` | R=2，子力>10 时才启用，防误判 |
| **剃刀剪枝（Razor）** | `search():234-241` | 浅层非 PV 节点快速放弃劣着 |
| **置换表（TT）** | `tt.ts` + `search():204-214` | Zobrist 哈希查表，避免重复搜索 |
| **杀手着法** | `killerMoves` + `updateKiller()` | 同层非吃子好着优先 |
| **历史启发** | `historyTable` + `updateHistory()` | 衰减式加分，容量上限 1<<16 |
| **着法排序** | `orderMoves():143-185` | TT 着法 > MVV-LVA 吃子 > 杀手 > 历史 > 暗子翻开加成 |
| **将死/困毙判定** | `search():226-231` | 无合法着法：被将→`-MATE+ply`，否则和棋 |

静态搜索内部也做了 **MVV-LVA 排序 + Delta 剪枝**，并对送将着法（`isInCheck`）直接跳过。

### 1.3 局面评估（`src/ai/evaluate.ts`）

定位为"精简高效"，主要为搜索深度让路：

- **子力价值**：帅 10000、车 900、炮 450、马 400、相/仕 200、兵 100；暗子按 `价值*0.75 + 15` 折价（不确定性惩罚）。
- **位置价值表（PST）**：车/马/炮/兵 四套 10×9 表，鼓励大子活跃、兵过河。
- **国王安全**（`kingSafety`）：九宫护卫 +15/子、出宫 -40、正面被车/炮直瞄 -50；按局面阶段加权。
- **局面阶段**：统计大子数，`phaseFactor = min(1, majors/8)`，残局弱化国王安全权重。
- **主动去掉了机动性计算**（每子 `getLegalMoves` 太慢，拖累深度）。

### 1.4 走法生成与规则（`src/engine/moves.ts`）

- `getAllLegalMoves` → 逐子 `getXxxMoves` → 过滤"走后己方被将"的着法。
- **飞将（将帅照面）**已补齐：新增 `kingsFaceEachOther()`，在 `isInCheck()` 中判定照面即视为被将，从而自动拒绝非法着法。
- 揭棋特有：暗子首次移动会**翻面揭示**（`hidden=false`），评估与排序都对暗子做了折价/加成处理。

### 1.5 底层支撑

- **Zobrist 哈希**（`zobrist.ts`）：xorshift32 固定种子生成 `pieceKeys[type][color][row][col]` + `sideKey`，`computeHash` 全量计算，`updateHash` 增量更新（目前搜索主路径仍用全量 `computeHash`）。
- **快速网格克隆**（`utils.ts`）：手写循环只克隆 grid 的少量字段，避免 `cloneBoardState` 拷贝 `moveHistory/captured` 等无用数据，搜索核心开销大幅降低。
- **记谱与导出**：`notation.ts` 生成中文纵线记谱（车二平五…），`utils/exportGame.ts` 支持 TXT/JSON 导出。

## 二、调研结论：现状与瓶颈

### 2.1 已经做得不错的地方

1. 搜索框架**工程完备**：PVS + QS + TT + Null-Move + 杀手/历史 + 迭代加深，已接近业余强引擎骨架。
2. **持久化 Worker + 跨回合 TT**：算力利用效率高，3 秒内常能搜到 depth 6，TT 命中率可达 70%+。
3. **规则正确性**：飞将、翻面、将军/将死均已实现。

### 2.2 当前棋力的真正瓶颈

| 瓶颈 | 影响 | 严重程度 |
|------|------|----------|
| **揭棋"暗子"信息未利用** | AI 把对手暗子近似等概率猜测，开局/中局对"对方可能是车还是马"没有任何概率建模，导致关键决策盲目 | ★★★★★ |
| **评估函数偏薄** | 缺机动性、缺棋子协调/牵制、缺过河兵威胁链、缺"捉双/抽将"等战术直觉；仅靠 PST | ★★★★ |
| **搜索深度受限（6 层）** | 揭棋子力多、分支大，6 层对复杂战术仍不够；且 QS 只算吃子，不含"将军延伸" | ★★★★ |
| **无开局库** | 前若干步纯靠搜索，既慢又易走出非主流布局 | ★★★ |
| **无残局知识/表** | 子少时评估粗糙，易走和/走输简单残局 | ★★★ |
| **增量哈希未接上** | 每步 `computeHash` 全量扫描 90 格，搜索越深越浪费 | ★★ |

> 一句话：现在的 AI 是"一个正确但经验不足的棋手"——规则懂、框架对，但对**揭棋特有的暗子博弈**和**局面理解**还停留在通用象棋近似水平，这是它"显得弱"的核心原因。

### 2.2.1 关于"暗子"的深入说明（揭棋核心难点）

普通中国象棋引擎可以直接评估"对方车在这个位置很危险"。揭棋里对方未翻开的子可能是车、也可能是兵，AI 当前做法：
- 评估上：暗子统一 `价值*0.75 + 15` 折价 —— 丢掉了"这个暗子有 1/7 概率是车"的信息。
- 搜索上：把暗子当确定类型展开，不会"假设对方翻出车后我方如何应对"。

这正是揭棋 AI 与普通象棋 AI 的本质差异，也是优化收益最大、最区别于通用方案的切入点。

## 三、优化方案（路线图）

按"投入产出比"排序，建议分阶段落地：

### 阶段 A：暗子感知（收益最大，揭棋专属）

**A1. 暗子概率评估**
- 在评估时，把对手暗子按"尚未翻出的剩余棋子分布"赋予**期望价值**，而非固定折价。
- 维护一个 `remainingHidden: Map<PieceType, count>`，每翻开一个暗子更新；评估时对单个暗子用 `Σ P(type)·value(type)`。
- 预期：中局决策质量显著提升，不再"怕错暗子"。

**A2. 翻面着法特殊处理**
- 当前所有着法平等排序；应提升"能翻开关键暗子（可能吃子/将军）"的着法优先级。
- 可引入 **蒙特卡洛浅采样**：对含暗子的分支，按概率抽样几种"暗子真实身份"分别评估取期望（轻量级，每节点几样本）。

### 阶段 B：评估深化（稳健提分）

**B1. 恢复廉价机动性**
- 改用"攻击格计数"替代全 `getLegalMoves`：预先生成各子攻击位图，统计可控格数，成本低很多。
- 加入：棋子协调（车占肋、马据相口）、兵过河威胁链、被牵制惩罚。

**B2. 威胁/战术特征**
- 计算"对方下一步能吃我什么"的静态威胁表，作为评估项；让 AI 有"别送子"的直觉。

### 阶段 C：搜索增强（更深更准）

**C1. 将军延伸（Check Extension）**
- 遇到将军时 `depth+1`，避免战术线被截断；配合 QS 能抓到更多杀着。

**C2. 增量 Zobrist 哈希**
- 搜索主路径改用 `updateHash`，省掉每步 90 格全量扫描；预计搜索节点速度 +20%~30%，等效于免费提 1 层深度。

**C3. 提升时限/深度自适应**
- 按剩余子力动态调整 `timeLimit`：残局给更多时间精算；开局适当缩短。
- 目标 `maxDepth` 提到 7~8（TT 命中率上来后自然可达）。

**C4. 开局库**
- 内置 5~8 步主流布局表（炮二平五/兵三进一等），前几步查表省下搜索给中后盘。

### 阶段 D：终极方案（若仍不满意）

**D1. 接入专业引擎 Pikafish 的揭棋分支**
- Pikafish / 皮卡鱼 已有完整 C++ 评估与搜索，ELO 3000+；可 WASM 编译直接在浏览器运行，棋力碾压自研。
- 成本：需为"暗子"建模（Pikafish 支持变体配置），工作量较大但是"一步到位"。
- 残局可叠加 **Syzygy 残局表**（6 子内必和/必胜）。

## 四、优先级建议

| 优先级 | 项 | 预期提升 | 工作量 |
|--------|-----|----------|--------|
| **P0** | A1 暗子概率评估 | 中局决策质变 | 中 |
| **P0** | C2 增量哈希 | 搜索速度 +25% | 低 |
| **P1** | B1 廉价机动性 + 协调 | 评估更准 | 中 |
| **P1** | C1 将军延伸 | 抓更多杀着 | 低 |
| **P2** | A2 翻面 MC 采样 | 暗子博弈更稳 | 高 |
| **P2** | C4 开局库 | 开局更专业 | 中 |
| **P3** | D1 Pikafish-WASM | 棋力天花板 | 高 |

**结论**：先做 **P0（暗子概率评估 + 增量哈希）**，这两项改动小、直击揭棋核心弱点，能在不增加复杂度的前提下让 AI 明显"变聪明"；再视效果推进 B/C 阶段。若产品要求"职业级"棋力，直接走 D1。
