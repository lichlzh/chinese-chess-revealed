## 一、当前实现：架构概览

```
UI 落子 → gameStore.requestAIMove()
            └─> aiManager.requestMove(state, {maxDepth:6, timeLimit:3000}, timeout 5000)
                   └─> Worker（常驻，跨回合复用同一个 TranspositionTable）
                          └─> sanitizeState(state)   ← 脱敏：暗子 type 替换为「位置身份」
                                 └─> findBestMove()
                                        ├─ 迭代加深 depth 1→6 + 期望窗口 ±150
                                        ├─ PVS + 静态搜索 + 剃刀剪枝
                                        └─ 返回 {from, to}
```

| 模块 | 文件 | 职责 |
|------|------|------|
| 搜索核心 | `src/ai/search.ts` | Negamax/PVS/QS/剃刀/重复裁决/着法排序 |
| 局面评估 | `src/ai/evaluate.ts` | 子力 + PST + 国王安全 + 阶段加权 |
| 置换表 | `src/ai/tt.ts` | `Map<number, TTEntry>`，上限 1<<20 |
| 哈希 | `src/ai/zobrist.ts` | Zobrist，增量 `updateHash` 已接入搜索热路径 |
| Worker | `src/ai/worker.ts` | 持久化 + **脱敏** |
| 调度 | `src/ai/manager.ts` | Worker 生命周期、超时 |
| 走法生成 | `src/engine/moves.ts` | 合法性、将军/飞将、长将长捉 |
| 重复裁决 | `src/engine/repetition.ts` | 局面指纹、三次重复裁决 |

搜索已具备：迭代加深、PVS、置换表、杀手/历史启发、MVV-LVA、Delta 剪枝、静态搜索、重复局面感知（长将/长捉）。
**框架层面是完备的**，问题出在「暗子建模」与「单节点开销」两处。

## 四、最严重的问题：翻面身份建模错误

### 4.1 代码链路

1. `worker.ts:37` `sanitizeState()` 把每个暗子的 `type` 替换为**该格的位置身份**：

```ts
if (!cell.hidden) return { ...cell };
const identity = getPositionIdentity({ row: r, col: c });
return { ...cell, type: identity ?? cell.type };
```

2. `search.ts:60` `applyMove()` 移动时翻面：

```ts
if (piece.hidden) piece.hidden = false;   // type 保持不变 = 位置身份
```

3. `evaluate.ts:120` 评估按 `hidden` 分支：

```ts
const val = p.hidden ? HIDDEN_PIECE_VALUE : pieceEval(p.type, r, c, p.color);
```

### 4.2 后果

脱敏本身是**正确且必要**的（AI 不该偷看暗子）。但**脱敏方案选错了**：

- 暗子在翻面前：按位置身份走子（规则正确），评估按 320。
- 暗子翻面后：`type` 仍是位置身份 → **AI 认为「车位的暗子翻开一定是车，兵位的暗子翻开一定是兵」**。

而真实规则是：暗子翻开后是从剩余池中**随机**得到的真实兵种，与所在格位置**完全无关**。

于是 AI 的搜索树里：

| 场景 | AI 的信念 | 现实 |
|------|----------|------|
| 我走车位暗子 | 得到车（+900，Δ≈+580） | 期望 320 |
| 我走兵位暗子 | 得到兵（+100，Δ≈−220） | 期望 320 |
| 对方车位暗子 | 是车，要防 | 只有 2/15 概率是车 |
| 对方兵位暗子 | 是兵，可无视 | 同样可能是车 |

**AI 几乎只经历「翻出来的正好等于位置身份」这一个世界，对揭棋最本质的不确定性——"兵格里可能是车"——零建模。**

### 4.3 与历史观测相互印证

此前 100 局自对弈统计的红方首步分布中，主导着法正是：

- `炮8进7（翻）`、`炮2进7（翻）` ← 炮位暗子深进
- `车1进1（翻）` ← 车位暗子

这与上述偏置的预测**完全一致**：AI 误以为走车/炮位暗子能"翻出大子"，因此系统性地抢着动车/炮位，回避兵/士/象位。

> 这解释了此前"AI 开局在人类看来很怪"的现象，根因不是搜索深度，而是**世界模型错了**。

### 4.4 为什么不能简单改评估

一旦暗子翻面，它后续的**走法**由真实兵种决定。若不在搜索里确定真实身份，就无法生成它下一步的走法。
因此**单棵搜索树 + 期望值**的做法在 2 层以上就不成立，必须引入**采样 / 确定性化**。

## 六、优化方案

### Tier 1 —— 正确性 + 白捡的深度（建议先做，约 1–2 天）

**1.1 走法生成提速（最大杠杆，200 µs → 目标 <30 µs）**

- `getLegalMoves` 改用 **make/unmake 原地修改**，去掉每个候选目标的全盘 `cloneGrid`。
- 预筛**被牵制子**：只有「移动的棋子可能暴露己方将」时才做完整合法性检查，其余直接放行。
- `isInCheck` 改为**从将位出发的反向射线检测**（车/炮/马/兵/将 五类），把 O(90×走法生成) 降为 O(常数)；或每节点算一次 90 格「被攻击位图」复用。
- 缓存将/帅位置，避免 `findKing` 反复全盘扫描。
- 为静态搜索单独提供 `generateCaptures()`。
- **预期：等效 +1.5~2 层深度，是所有改动里收益最确定的一项。**

**1.2 消除 positionKey 的每节点开销**

- 重复指纹改用**增量 Zobrist**（复用已有的 `updateHash`），去掉每节点/每边构造 90 字符串（40–60 µs/节点）。
- 顺带把 `computeHash` 也换成增量（0.57 µs，收益小但几乎免费）。

**1.3 修翻面身份模型**

分两步：

- **过渡版（半天）**：`HIDDEN_PIECE_VALUE` 由固定 320 改为**剩余池的超几何期望值**（每翻开/吃掉一枚即更新信念）；翻面后的子按期望值估值，并加"信息增益"奖励。能去掉最歪的偏置，但**不解决翻面后的走法生成**。
- **正解（配合 1.1 提速后）**：**根层确定性化（PIMC）**
  - 维护 `belief: Record<Color, Map<PieceType, number>>`（每方 15 枚的剩余分布）。
  - 每回合采样 K 个与已知信息一致的「真实棋盘」（K=4~8），各自跑现有 alpha-beta。
  - 按 `mean − λ·std`（或最坏情况）聚合选步，**λ 用于缓解 strategy fusion**（PIMC 的已知缺陷：它会"幻想"自己能在不同世界采取不同策略）。
  - **注意：各样本的 TT 不能共用**（不同确定性化是不同的真实状态），否则结果不sound。

**1.4 清理并启用空着裁剪**

- 修 `search.ts:357` 的 `!repetitionAware` 条件（根调用恒为 `true`，导致永不触发）；若无法在重复感知下安全启用，直接删除以免误导。

**1.5 搜索增强三件套**（均为低风险小改动）

- **将军延伸**：被将时 `depth + 1`，避免杀着被地平线截断。
- **LMR**：depth ≥ 3、第 4 着之后、非吃子/非将军/非 PV → 深度减 1（失效则重搜）。
- **Futility 剪枝**：前哨节点按静态评估 + 余量直接剪掉。

### Tier 2 —— 评估深化（约 3–5 天）

- **信念池 + 超几何更新**做完整版（Tier 1 若只做了过渡版）。
- **廉价机动性**：复用 1.1 产出的攻击位图，几乎零额外成本就能统计可控格数。
- **威胁与战术特征**：悬子、牵制、捉双、被攻击且无根的子。
- **渐进式（tapered）评估**：目前只有 `kingSafety` 乘了 `phaseFactor`，子力价值与 PST 应同样分阶段插值。
- **暗子期权价值**：未翻的暗子兼具"位置身份走法"与"随机真实身份"两重属性，应单独建模其灵活性。

### Tier 3 —— 架构级（周级，量力而行）

| 方案 | 说明 | 适配度 |
|------|------|--------|
| **信息集 MCTS（SO-ISMCTS）** | 每条模拟线只确定性化一次，天然适配不完美信息；随思考时间平滑变强，无 alpha-beta 的深度硬约束 | **最契合揭棋**，但需重写搜索 |
| AlphaZero 自对弈 | 参考 `xreal.cc` 的 JIEQI-AZ：C++ 引擎 + PyTorch + 16 进程自对弈，训练后导出小网络到浏览器 | 上限最高，算力/工程量最大 |
| 集成皮卡鱼揭棋引擎 | 已知存在「皮卡鱼揭棋 23.1.11」构建，棋力达业余高段 | 它是**原生 UCI 二进制**，浏览器需 WASM 移植，且难以按本项目规则魔改；**更适合作强度参照/离线分析，不建议直接嵌入** |

## 七、建议落地顺序

1. **1.1 走法生成提速** —— 收益最确定，且是后面所有改动的前置（PIMC 会把 3s 切成 K 份，没有提速就没深度）。
2. **1.2 增量重复指纹 + 1.4/1.5 搜索三件套** —— 小改动，再换约 1 层深度。
3. **1.3 翻面身份建模** —— 先过渡版，提速完成后上 PIMC。这一步是"AI 从不会下揭棋 → 会下揭棋"的分界。
4. Tier 2 评估深化。
5. 视效果决定是否上 Tier 3。

## 八、如何验证"真的变强了"

现有 `src/selftest/selfplay.test.ts` 是**正确性**harness（`maxDepth:3, timeLimit:60`，校验合法性与终局不变量），**不是强度 harness**，不能用来判断棋力。

建议补一个 A/B 对战脚本：

- 固定一组开局随机种子（保证新旧 AI 面对同一批局面）。
- 新 AI vs 旧（基线）AI，**互换先后手**各 N 局，消除先手优势。
- 统计胜/负/和，胜率显著 >50% 才算提升。
- 每次改动跑一遍，避免"感觉变强了"。

> 没有这个 harness，Tier 1~3 的每一条都无法客观排序。

## 附：参考调研

- **揭棋是不完美信息博弈**，需搜索「信息集树」而非「真实博弈树」；节点存信息集哈希，模拟时再从信息集抽样具体状态。
- **确定性化（PIMC）** 的经典缺陷是 **strategy fusion** 与 **non-locality**；`IIMCS`、`SO-ISMCTS` 是为修正它而提出的主流改进。
- 翻翻棋/揭棋类 AI 的常见工程路径：位棋盘 + Zobrist + 剩余棋子计数表（概率模型）+ 信息集 MCTS + 启发式 rollout 策略。
- 自对弈 + 神经网络（AlphaZero 范式）是该品类的强度上限，已有类似方向的揭棋引擎实践。

## 九、验证记录

### 2026-09-20：增量 Zobrist 哈希接入搜索热路径

**改动**：`src/ai/search.ts` 中 `search()` 和 `quiescence()` 不再每节点调用 `computeHash(grid, turn)`（O(90) 全棋盘扫描），改为通过 `updateHash()` 在 makeMove/unmakeMove 时 O(1) 增量更新哈希值，沿递归链传递。

**动机**：原 `computeHash` 每节点耗时 572 ns，虽占比 <0.3%，但深度 4+ 全对局搜索时会触发栈溢出（QS → search 递归过深）。增量哈希将每节点哈希开销降至 O(1)，显著减少单节点总耗时，从而允许更深搜索。

**验证结果**：
- `search-inv.test.ts` 4/4 通过（确定性、合法性、不变量）
- 深度 4 单步搜索：95,800 节点，10 秒完成，无栈溢出
- 深度 4 单步搜索（缓存命中）：70,149 节点，2.6 秒完成
- 对比：优化前深度 4 全对局搜索会触发栈溢出

**关键数据**：
| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 每节点哈希开销 | 572 ns（全扫描） | ~50 ns（增量 XOR） |
| 深度 4 单步 | 栈溢出 | 10 秒完成 |
| TT 命中率 | 3–5% | 5–9%（增量哈希更稳定） |
